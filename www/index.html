WS-агрегатор

N источников → агрегация → один выходной WebSocket

Документация Демо

Обзор

Многопоточный WebSocket-агрегатор на C17: принимает N входящих WebSocket-соединений источников, агрегирует их сообщения и отправляет результат в единственный выходной WebSocket. Обе стороны — источники и выходной WS — сами подключаются к серверу; сервер никогда не выступает WS-клиентом. Раздачи статики в проекте нет — сервер целиком посвящён WebSocket (RFC 6455).

  • Архитектура: SO_REUSEPORT + Task Queue + Thread Pool (приём) + отдельный поток-агрегатор (выход)
  • Платформа: Linux
  • Язык: C17, без внешних зависимостей (свои SHA-1/base64 для рукопожатия)
  • I/O: epoll() с EPOLLET + EPOLLONESHOT на приёме, отдельный epoll в потоке-агрегаторе
  • Backpressure: источники приостанавливаются (park/resume), если выходной WS не успевает — данные не теряются

Возможности

WebSocket-рукопожатие

RFC 6455 п.4: Sec-WebSocket-Accept на своих SHA-1/base64, коды 101/400/426

Полный кодек кадров

Фрагментация, управляющие кадры между фрагментами, PING/PONG, CLOSE с кодом

Валидация UTF-8

Инкрементальная проверка TEXT-сообщений по границам фрагментов (RFC 3629)

SO_REUSEPORT

Ядро распределяет входящие подключения между Listener потоками

EPOLLONESHOT

Гарантия «одно соединение — не более одного потока одновременно» без мьютексов на сокете

Backpressure без потерь

Park/resume источников по водяным знакам вместо буферизации без предела или дропа

Архитектура

  ws1 ─┐   accept          ingest-epoll (ET+ONESHOT)        Queue<Conn*>       worker pool
  ws2 ─┤ ───────────────►  listener'ы                 ─────────────────────►   парсинг WS-кадров
  ...  │                                                                            │
  wsN ─┘                                                                            │ Msg_t
                                                                     dataQueue (Queue_t) + eventfd
                                                                                     │
                                                              ┌──────────────────────┘
                                                              ▼
                                                   ┌── поток-агрегатор (один) ──┐
                                                   │ epoll: dataQueue, ctrlQueue,│
                                                   │  sink-fd, timerfd          │
                                                   │ aggOnMessage()/aggOnTick() │──► выходной WS
                                                   │ park/resume источников     │    (принят нами же)
                                                   └────────────────────────────┘

Источники остаются под пулом воркеров (параллельная обработка); выходное соединение обслуживает единственный поток-агрегатор — это единственный писатель в единственный sink-сокет, поэтому кадр кодируется один раз и не требует мьютексов при отправке.

State Machine соединения

┌────────────────────┐   заголовки    ┌────────────────────┐
│  ST_HANDSHAKE_READ  │───полностью───▶│  ST_HANDSHAKE_SEND │
└────────────────────┘   получены     └──────────┬──────────┘
                                                   │ 101 отправлен
                              ┌────────────────────┼────────────────────┐
                              ▼ role=SOURCE                              ▼ role=SINK
                    ┌────────────────────┐                    передача агрегатору
                    │     ST_WS_OPEN     │                    (DEL из ingest-epoll,
                    │  разбор WS-кадров, │                     ADD в epoll агрегатора)
                    │  backpressure      │
                    └────────────────────┘

Маршруты

Путь Кто Описание
--sink-path (по умолчанию /feed) выходной WS Единственный приёмник агрегированного потока; новое подключение замещает предыдущее (CLOSE 1001)
любой другой путь с Upgrade: websocket источник id источника сервер присваивает сам; сообщения тегируются и пересылаются приёмнику
запрос без Upgrade — 400 Bad Request — статики сервер не отдаёт

Использование

# Сборка
make

# Запуск
./httpserver -p 33333 -w 8 -l 2 --sink-path /feed

# Тестовый клиент (чистый stdlib, см. tests/ws_client.py)
python3 tests/ws_client.py sink ws://127.0.0.1:33333/feed
python3 tests/ws_client.py src  ws://127.0.0.1:33333/s1 --rate 5

# Протокольные негативные кейсы (RFC 6455)
python3 tests/ws_client.py fuzz ws://127.0.0.1:33333/s1

# Живое демо в браузере
open www/ws-demo.html   # открыть напрямую, сервер эту страницу не раздаёт
